# ADR 0014: Catalog and inventory schema, database-enforced invariants, DB testing

Status: Accepted (2026-10-15). Implements ADR 0008 (stock), 0009 (specs) and 0010 (bundles) in M2a.

## Schema decisions

- **IDs**: UUIDv7 generated by Prisma (`@default(uuid(7))`, column type `UUID`): time-ordered for index locality, no sequence to guess.
- **Money**: `INTEGER` piastres everywhere (max about 21.4 million EGP, aligned with `domain/money.ts#MAX_PIASTRES`). Never floats, never strings.
- **One `product` table** for physical goods, bundles and (later) gift cards/digital: `type` + `status` + `deletedAt` (soft delete). Bundle components live in `bundle_item`; stock lives in `inventory` (physical only). **There is no stored "reserved" or bundle-stock number**: both are derived by SQL views, so they cannot drift.
- **Categories** keep a unique materialized `path` ("components/cpus/amd-ryzen", depth 1 to 3) that matches the storefront URL; specs are JSONB validated against `spec_definition` rows (ADR 0009).
- **Slugs, SKUs and barcodes are unique among non-deleted products** (partial unique indexes), so soft delete frees them. Prisma cannot express partial indexes: they are raw SQL and are not in `schema.prisma`, hence products are looked up with `findFirst({ deletedAt: null })`, not `findUnique`.

## Invariants enforced by the DATABASE (not only the app)

CHECK constraints: formats of slug/SKU/barcode, non-negative money and stock, `compareAtPrice > price`, the product pricing shape per type and bundle mode (every branch spells out `IS NOT NULL`, because a CHECK passes on NULL), showcase blocks needing alt text in both languages, https-only video URLs, spec-definition consistency.
Triggers: bundle components must be PHYSICAL and the parent a BUNDLE (no nesting); inventory only for PHYSICAL products; a product's type cannot change while stock, reservations or bundle membership depend on it; stock history (`inventory_adjustment`) is append-only; a reservation's product and quantity are immutable and a resolved reservation never changes state again.
Foreign keys: a component or category in use cannot be hard-deleted (RESTRICT); deleting a bundle cascades to its items.
Views: `product_availability` (physical = onHand minus active unexpired reservations; bundle = min over components of floor(available / quantity), 0 if any component is not ACTIVE or is deleted, 0 with no components; gift cards NULL) and `product_pricing` (bundle price derived from CURRENT component prices; percent discounts round half away from zero). Listings join both views in one query (no N+1). Each view has a TypeScript twin (`bundleMaxSellable`, `quoteBundle`) and a randomized DB test proves they agree.

## Time zones (a real portability trap)

Prisma stores `DateTime` as UTC in `timestamp` (no zone) columns. Comparing such a column with `now()` converts using the SESSION time zone, which is Cairo on many Windows installs, so a naive view would mark live reservations expired (silent overselling) or vice versa. Rules: SQL uses `timezone('UTC', now())`; raw SQL passes `"…Z"::timestamp` literals; services always pass an explicit `now` and set `createdAt` themselves; no CHECK depends on a `DEFAULT CURRENT_TIMESTAMP`. The whole DB suite is run with both Node and the database session in UTC, Africa/Cairo, America/Los_Angeles and Pacific/Kiritimati (+14).

## Stock operations

Every operation that can change availability first locks the affected inventory rows with `SELECT … ORDER BY "productId" FOR UPDATE` (ascending id, deadlock-free), then re-measures availability under the lock, then writes. Multi-product operations are one transaction and all-or-nothing. Bundle lines expand into components and demand is aggregated across the whole cart before checking. `convertReservations` is idempotent (webhook retries) and reports `UNFULFILLABLE` (changing nothing) when a late payment finds its stock gone. Functions accept an optional `tx` so M6b can create the order and take stock in one transaction.

## Hand-written migration

The Prisma engines cannot be downloaded in the authoring sandbox, so `20261014000000_catalog_inventory` was written by hand following Prisma's naming (`<table>_pkey/_key/_idx/_fkey`, `TIMESTAMP(3)`, `ON UPDATE CASCADE`). It was executed on a real PostgreSQL 18.4 and exercised by 105 DB tests, but **drift against `schema.prisma` cannot be checked without the engine**: the owner runs `prisma migrate dev` and `prisma migrate diff --exit-code` locally (README), and CI runs the same diff on every push. SQL is kept compatible with PostgreSQL 15+ (Supabase, local, CI's `postgres:17`).

## DB testing (`npm run test:db`)

A separate Vitest config runs `tests/db/**/*.db.test.ts` serially against a database that must be local, end in `_test` and differ from the development database (host aliases normalized). Global setup creates it if missing, drops and recreates `public`, and applies every migration SQL file directly with `pg` (no engine needed, and it doubles as a check that the SQL is valid). Workers get `DATABASE_URL` overwritten with the test URL, and the table reset re-checks `current_database()`.

## Image storage

`StorageProvider` interface (`put/delete/exists/urlFor`), keys not URLs in the database, content-addressed keys, content sniffing by magic bytes (the declared type is never trusted), SVG refused for uploads, 5 MB cap, atomic local writes confined to the root. Only `local` is implemented; `supabase` and `cloudinary` throw a clear "not implemented" error until M10a.

## Consequences

- Business rules that must never be violated live in the database as well as the app; tests attack them directly.
- Prisma Studio or hand-written SQL cannot corrupt stock, bundles or history.
- Raw SQL is used for locking, aggregation and the views; every such query lives in `server/repositories`.
